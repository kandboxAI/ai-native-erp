# 数据库维护：按当前模型生成本环境差异

## 日常只做三步

在仓库根目录执行，t_actual 替换为实际租户；Linux 将 python 换成 python3：

```text
python scripts/erp.py db revision --plugin mes --schema t_actual
```

**审核输出文件**中的新增/删除字段、外键、默认值和数据回填，再执行：

```text
python scripts/erp.py db upgrade --plugin mes --schema t_actual
```

之后启动服务，在「应用管理」升级或启用对应套件。选定插件时命令包含底座和该插件的依赖。省略 `--plugin` 时处理当前部署中的全部范围，多租户逐个 schema 执行。

## 文件与版本

| 内容 | 存放与处理 |
| --- | --- |
| 固定基线、已发布历史 | plugins/core/backend/alembic/versions/，保留版本号；不在日常开发中改写 |
| 环境增量 | plugins/core/backend/.local-migrations/<数据库标识>/<schema>/<范围>/，Git 忽略，不能随数据库备份丢失 |
| 业务数据转换 | 随所属插件维护可审核的转换逻辑，由本环境迁移显式调用；自动比较不能推断身份映射 |

数据库标识由主机、端口和库名计算，不含账号密码。连接地址变更、换机器或恢复数据库时，一并恢复对应环境目录；不能只拷贝数据库或把另一套数据库的增量直接拿来执行。

新流程使用独立的 public/租户范围版本表（auth_model_version、sys_model_<范围>_version），不改写旧 auth_alembic_version / alembic_version，也不要求升级到旧共享链的最新头。它们是迁移工具内部表，不是业务模型。

## 新环境与失败处理

- 新库先按[底座说明](core-open-source.md)执行 init，再做上面的生成、审核、升级。已有库不重新初始化。
- 没有差异不生成空版本；已有未执行的本地迁移时，先审核并执行，再生成下一次差异。
- upgrade 不自动生成 SQL；执行后仍有模型差异会报错，不会把插件标记为就绪。各范围独立提交，失败不会假装整组已回滚。
- 迁移已执行但仍报模型不一致：查看输出的剩余对象，再生成、审核并执行补充迁移；保留已执行文件。旧生成器在新建表时曾漏建 `use_alter=True` 的延迟外键，更新代码后补一次差异即可，不需要重建库。
- 建表时报 `42P01`（引用的表不存在）：检查是否因循环外键而先建了明细、后建主表。生成器会将指向稍后新建表的外键移到建表之后；旧的未成功迁移须审核修订后重试，更新生成器不会自动修改已有文件。
- 本地已执行文件缺失时从备份恢复，不删除版本记录，不用 stamp。版本查看：`python scripts/erp.py db current --plugin mes --schema t_actual`。
- 自动比较不删除模型之外的整表；字段重命名、拆表与业务数据转换仍须人工审核。需要纯数据转换时，可用 plugin_cli revision（不带 --autogenerate）生成本地空迁移。
- 服务启动不执行迁移；应用管理只执行已有本地文件并检查模型，不替你生成或审核。插件版本和租户启停仍由应用管理记录。

所有 db 命令先显示目标并确认；自动化用 --yes --database 实际库名。生成会读取数据库，但不执行生成的业务 DDL；upgrade 才写数据库。表/接口变更后按[Harness 同步](harness-sync.md)更新检索。


## 插件升级说明

各插件在自己的文档中维护模型差异、数据回填和历史兼容说明。生成迁移后，结合目标数据库审查约束、索引、非空字段及既有记录的回填路径。对字段裁剪、合并关系等无法无损降级的变更，按升级前的备份制定回退方案。
