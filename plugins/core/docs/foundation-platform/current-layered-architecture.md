# ERP 整体分层设计（当前开源架构）

职责按 L1 / L2 / L3 划分，业务源码统一保存在所属 `plugins/<key>/` 内，Python 导入名称保持稳定。本文说明当前边界；原分层设计的完整规划已恢复在本目录 erp-layered-architecture.md，入口见 [文档索引](README.md)。

| 层次 | 职责 | 分发方式 |
| --- | --- | --- |
| 技术基础设施 | 配置、异常、会话、租户上下文、模块与路由收集 | 随底座；core/、framework/ 保持通用 |
| L1 管理底座 | 认证、用户、组织、授权、字典、菜单、流程、通知、文件、审计和通用 AI | 随底座；实际模块清单为 core_manifest.json |
| L2 公共业务 | 库存、人事、应收、设施、工单等模块职责 | 按实际复用需求独立发布或随行业插件交付；当前 inv 独立，hr/ar/fac/tkt 随 EDU |
| L3 行业业务 | 制造、教育等行业对象和流程 | 独立插件，可依赖 L1 / L2 |

## 依赖与数据拥有者

职责分层与发布粒度分别决定。EDU 统一包含教育和 hr/ar/fac/tkt 模块，保持内部 Service 与数据边界，只依赖共享 inv；不为潜在复用强制维护多个插件版本。原四个插件迁移作为兼容历史保留，后续变更统一进入 edu。详见归并说明（开发仓库/插件中的 `../edu-consolidation.md`，未随纯底座分发）。

- L1 不反向依赖 L2/L3；通用外壳不写学生、班级、工序等行业规则。
- L2/L3 插件通过 plugin.toml 明确依赖；跨模块写入调用拥有者的公开 Service 或事件，跨模块读取具有权限、范围与字段契约。
- 共同表前缀不等于共同归属。主体、自然人等 md_ 对象属于 L1；物料和供应商由相应 L2 插件维护。
- 行业扩展优先建立自己的关联/扩展表，不把制造或学校字段塞进通用身份、组织及库存表。

## 同一租户中的数据

所有已安装业务与底座表可位于同一个租户 schema，以表前缀和模块归属区分。L1、L2、L3 不各建一个 schema；租户之间以 t_<编号> 隔离，public 仅保存认证和租户目录。

纯底座不创建业务表。部署组合决定可装配的插件代码；租户安装及启用决定目标租户可用的能力；最终接口还检查用户权限和数据范围。详见 [插件架构](current-plugin-architecture.md)、[数据库设计](core-database-design.md)。

位置信息作为 inv 内部共享模块提供一个维护菜单，资产、仓库和 EDU 巡查共用；沿用现有 inv 交付及迁移流程。坐标必填及历史位置关联见位置维护说明（开发仓库/插件中的 `location-master-design.md`，未随纯底座分发）。
