# 能力包（插件）架构：当前契约

L1 是底座，L2/L3 以独立源码插件接入。旧文档中的预置学校/工厂组合及旧 tenant 全量基线不再作为新插件操作方式。

## 1. 文件与拥有者

AI 岗位扩展使用可选 `ai_context_providers` 声明本插件模块的本人岗位提供器，与资源发现 `ai_providers` 分离。协议及读取范围见 岗位模板与个人偏好（开发仓库/插件中的 `ai-user-context.md`，未随纯底座分发）。

领域/数据库主设计统一维护在 plugins/core/docs/foundation-platform/；插件 docs 保留随包说明或副本，修改主设计时同步相关副本。

```text
plugins/<key>/plugin.toml           key、版本、依赖、模块、路由、迁移、AI 提供器
plugins/<key>/frontend.json         页面归属、应用卡片、小程序提供器
plugins/<key>/docs/                 随包说明、设计副本和实现差距
plugins/<key>/backend/app/modules/<module>/  插件后端，导入名仍为 app.modules.*
plugins/core/backend/alembic/versions/plugins/<key>/  独立版本分支
plugins/<key>/web/src/              插件页面、API 和资源
plugins/<key>/miniprogram/src/      插件移动页面、API 和资源
```

新插件声明 `source_layout = "contained"`，脚手架、转换器及安装/构建器统一支持此布局；未声明的旧包按 legacy 读取。清单仍填写逻辑路径，迁移目录不搬迁。开发、资源引用及旧源码搬迁见[源码目录](../plugin-source-layout.md)。

package_files 只登记规则允许的额外文件；插件 docs 已位于拥有目录中，无须另加额外路径。打包器收集这些文档，导入器一并写入；已经产出的 ZIP 不会自动包含后来新增的文档。

管理端可通过菜单目录 `flex_form.route.meta.embeddedIn` 声明子配置所属主入口的 `menu_key`。用户菜单树仅在主入口也已授权且可见时折叠子入口，并设置子路由的 `activePath`；菜单配置页、存储数据、角色授权与路由注册保留。仅获授权使用子入口的账号仍可访问原入口。声明来自插件目录，由 L1 通用投影处理，不在底座写行业菜单名或权限旁路；修改后重启后端并刷新授权菜单即可生效，无需修改租户菜单数据。

菜单默认配置升级可用 `MenuDef.previous_permission_keys`、`previous_route_meta`、`previous_redirects` 声明已发布过的旧值。目录同步只在相同路径、非外链、未删除的页面上替换这些已知默认值；元数据或跳转不再声明时移除对应旧值，保留未列出的客户自定义配置。不含这些声明的菜单沿用原有补缺规则。若业务明确收紧页面权限，可通过角色菜单公开服务 `reconcile_permission_grants` 在同一事务内仅同步指定页面：按实际权限补授权及清理不匹配的旧绑定，不变更角色接口权限，内置管理员保留全部入口。

菜单声明可通过 `MenuDef.default_permissions_any` 指定按有效权限默认提供的公共入口。菜单树在请求时读取当前用户的真实权限并补入该入口及有效祖先，不修改角色菜单、接口权限或数据授权；未声明的菜单保持原有角色菜单规则，停用菜单、停用祖先及未启用插件仍不下发。该声明随后端代码生效，无需写库同步，适用于岗位等动态赋权的用户。

插件前端清单可用 `web_sidebar` 调整管理端导航分组。`anchors` 至少匹配一个已授权菜单才应用布局。`items` 以菜单标识引用入口，分组可用 `menu` 复用现有目录的显示名，或用 `title` 为新目录命名。布局只处理授权后可见的菜单，空分组不展示，未列入布局的可见入口仍保留。该配置随管理端构建生效，不需要同步数据库菜单。

## 2. 四个阶段

| 阶段 | 控制来源 | 行为 |
| --- | --- | --- |
| 源码安装 | 受检查的 ZIP、安装记录 | 合并源码及页面登记，不执行 SQL，不安装第三方依赖 |
| 部署装配 | 根 deployment.json 的 plugins | 明确列出全部依赖；空数组为 core，非空为 custom；修改后重启/构建 |
| 租户开通/升级 | public.auth_tenant_plugin | 检查依赖、执行迁移、同步目录及配置，成功才登记版本和可用状态 |
| 用户访问 | 后端权限、数据范围、原业务接口字段控制 | 每次请求执行；不因菜单可见或提示词说明而旁路 |

菜单及权限归属来自清单和目录声明，不按 /mes 路径、权限字符串前缀或角色名称猜归属。管理端和小程序按部署组合构建，租户停用保留数据及已发布包内代码，服务端拒绝访问。

插件可在 `catalog.py` 声明 `MENU_COMPOSITIONS`（`framework.menu_composition.MenuComposition`），在已授权的管理端响应树上合并重复导航、调整位置和附加路由参数。它不写数据库、不增加授权、不改变菜单拥有者；未授权目标、停用插件和自定义上级不强行合并。目录管理仍展示真实存储结构，收藏和旧隐藏路由保留。

`MenuComposition.hidden_placements` 可指定本次移动后不在管理端侧边栏显示的菜单标识。隐藏目录时，其下的入口也不在侧边栏展示，已有授权路由仍保留。组合未应用时，共享插件菜单仍沿用原布局。

需要保留共享菜单默认视图的插件，在自己的 `catalog.py` 声明 `MENU_VIEW_REQUIREMENTS = [MenuViewRequirement(plugin_key="自身标识", menu_key="共享菜单标识")]`，类型从 `app.framework.menu_composition` 导入。只收集当前部署、租户已启用插件的声明；有默认视图需求，或多个插件竞争同一来源时，保留原导航，不按导入顺序选择。插件只声明自身需求，不列举或排除其他行业插件；停用后声明不再生效。无需迁移或写入菜单表。

小程序 `pages.json` 可将业务页面登记在 `subPackages`；插件 `frontend.json` 仍登记原完整页面路径。`miniappPages()` 统一展开主包/分包路由，部署筛选、样式检查和运行时归属清单均使用完整路径；未选择插件的分包一并移除，tabBar 页面始终位于主包。消息跳转可由所属插件提供 `notificationTarget`，通用外壳不新增行业路径映射。

源码检查与打包也展开分包登记；包内页面记录可携带 `subpackage_root`，当前导入器保留已有页面自定义样式并将该插件页面迁入声明分包，旧包仍兼容。纯底座导出过滤业务分包。导航拦截保留插件、租户和身份复核，重放时使用静态 `uni.navigateTo/redirectTo/reLaunch/switchTab`，兼容 H5 API 按需编译。

业务页面更换组件时，可在所属插件的 `MenuDef.previous_components` 中登记系统曾下发的旧组件。普通页面只有在菜单 key、路径、类型与历史组件均匹配时，才在授权菜单响应中兼容为当前组件，并在显式菜单同步时持久化；不覆盖自定义组件、路径或外链，也不增加菜单或接口权限。页面升级为目录仍需显式同步，不在读取菜单时转换目录或补授子菜单。

模块可以在 `catalog.py` 声明 `RETIRED_MENU_KEYS`，退役入口由所属模块维护。通用菜单层按稳定 key 过滤已有租户授权导航及其子菜单，保留业务数据和历史授权；显式目录同步时才将这些菜单标记为停用、隐藏。底座不新增业务菜单名称或路径判断。

管理端默认菜单图标统一使用 Remix Icon 线框图标（`ri:`，通常以 `-line` 结尾），按菜单业务含义选择，不混用实心变体。菜单目录及其路由元数据中的图标应保持一致。替换默认图标时，在所属模块的 `MenuDef.previous_icons` 登记系统曾下发的旧值；授权菜单、菜单树及收藏入口按声明显示当前图标，保留空值和租户自定义图标，不修改数据库。重启后端并重新登录刷新菜单即可生效；需要持久化时显式执行开发配置同步，沿用历史默认值匹配规则，无需数据库结构迁移。

## 3. 模型、初始化与迁移

插件专属运行配置通过清单可选 `[configuration]` 声明变量前缀、公开模板和凭据变量。类型及默认值在插件中，实际文件在宿主 `plugins/core/backend/config/plugin/<key>.env`；通用加载、优先级、旧 `.env` 兼容及打包保护见[插件运行配置](../plugin-configuration.md)。未声明的旧插件保持原读取机制。该能力不改变租户业务参数的数据归属。

业务模块不要求独立发布。EDU 当前统一拥有教育及 hr/ar/fac/tkt 模块，依赖 inv；模块目录、Service、表前缀与权限保持稳定。它们不再是可单独启停的活动插件。历史兼容和维护入口见归并说明（开发仓库/插件中的 `../edu-consolidation.md`，未随纯底座分发）。

模型按拥有模块收集；表前缀不代替拥有者。专属子命名空间也包含其同名根实体：`xxx_record_` 覆盖 `xxx_record` 和 `xxx_record_version`，不覆盖 `xxx_recording`；清单前缀仍须以 `_` 结尾。仓库保留固定基线与已发布历史，日常增量按目标库现状生成到 plugins/core/backend/.local-migrations/，不提交 Git、不随包分发。

新流程按数据库、schema 和范围隔离版本表与文件，不追旧共享链的最新头。db revision 只生成；审核后 db upgrade 执行并校验模型；应用管理执行已有本地文件、检查结构并同步目录，不自动生成。新库先 init，已有库不重新初始化。命令与备份要求见[数据库维护](../database-workflow.md)。

原 tenant / tenant_core 共享版本表及所有已执行历史保留，仅用于兼容维护；本地未提交的旧增量保存在 .local-migrations/legacy/。新流程不删除旧记录、不 stamp，也不解析部署外业务的旧链来生成模型差异。

catalog 注册权限与菜单；dictionary_specs 注册字典；tenant_setup 幂等补齐必要配置；demo_seed 仅显式加载。插件服务启动不执行 create_all 或自动初始化数据库。

上层插件需要把依赖插件的既有页面组合进自己的业务导航时，在自身 `catalog.py` 声明 `MENU_PLACEMENTS`，只调整已有稳定 `menu_key` 的父级和顺序，不复制页面菜单或改变菜单归属。目标父级未参与当前部署时保留依赖插件的默认布局，因此下层插件仍可独立部署。

通用列表等复用组件可在模块的 `page_contracts.py` 导出 `PAGE_CONTRACTS`，声明路由实体参数、真实后端支持值、旧名称映射及接口未绑定项。完整插件校验和 `python scripts/erp.py check-pages` 均检查这些声明；结果只说明当前组件的接口绑定，不作为整个业务的完成度判断。页面须根据真实能力决定是否发起业务请求，绑定声明不能替代权限或数据范围校验。插件化先核对并接好已有代码，缺失业务实现只记录。实例见教育页面绑定范围（开发仓库/插件中的 `../education-page-status.md`，未随纯底座分发）。

迁移生成和升级分别授权；保留已执行版本，不能用 stamp 伪造升级。通用操作命令集中在 [接入手册](../business-plugin-integration.md)，AI 接入交付要求见 [任务单](../plugin-ai-onboarding.md)。

清单可选 `replaces = ["旧插件key"]` 表示归并已有 core 分支插件：新插件必须显式拥有其模块、路由、前端和表前缀。旧清单不参与活动注册；已发布旧基线随包保留；新流程按接管后的模型生成本环境差异，不再生成四个旧插件范围。只选择旧 key 不会隐式开通新插件；旧部署同时含新旧 key 时归一为新 key。新旧安装记录分开保留，新插件需显式成功升级到当前版本才开放归并后的模块。接管不能指向 core、自身、成环或被多个插件重复声明。

## 4. 通用 ERP / Harness 能力

业务待办通过模块 `todos.py` 的 `TODO_SOURCE`（`framework.todos.TodoSource`）提供：返回当前用户有权办理的前 N 条 `TodoItem` 及完整总数，按时间和稳定 ID 倒序。来源必须在自己的 Repository 过滤权限对应的数据范围和软删除。底座 `/api/system/my-todos` 聚合分页，自动排除未部署、租户未启用的插件；不在底座引用业务模型，也不代替原业务的提交/审核事务。现有流程审批和 MES 询价均已接入，待办办理后按源状态消失，无独立完成接口。

数据访问、接口调用及导航协议由通用集成提供。新业务声明自己的受控资源、接口、语义与菜单，不复制一套 Harness 数据/导航插件。技能归属可由插件 ai_skill_keys 声明；技能文件及宿主分发仍遵循其实际交付机制。

表/接口生成快照不提交 Git、不随源码包交付；目标环境迁移后独立同步快照、校验目录、按授权重建索引。迁移、启动及修改设计文档不自动调用模型或构建索引。

## 5. 发行边界

工作台近期日程可由插件的 `frontend.json.web_calendar_provider` 声明所属 `web/src` 内的 TS 提供器。提供器导出 `loadEvents(start, end)`，返回 `{id,date,time,title,description,path}` 列表；业务身份、课次语义和业务接口调用由插件维护。底座仅经 `virtual:workbench-calendar` 加载当前部署提供器并渲染通用日程，无提供器时显示暂无安排，不反向依赖教育业务。清单路径经 Python/JS 双端校验；API 目录提供器须按既有插件文件规则随包收集。

export_core.py 只导出 L1 和通用文档；pack 导出指定插件及其 docs，依赖插件另行导入。底座、插件、迁移版本、部署配置和目标租户状态需要分别核对，不能根据某份历史设计判断已经安装。

## 6. 业务套件

插件可在自己的目录提供 suite.toml，将根插件和 requires 的递归依赖组成一个源码交付单元。通用 `plugin_cli suite plan/deploy/pack/install` 负责依赖解析、合并显式部署和整包导入；不隐式改变运行时加载规则。

租户界面提供整套启用、升级、停用，复用独立迁移分支和 auth_tenant_plugin 记录；先预检再按依赖顺序执行，失败保留已完成状态并可重试。停用保留其他已启用插件所需的共享依赖。套件没有独立业务表、权限旁路或索引归属。操作见[套件说明](../business-suites.md)。


模块可在 `auth_grants.py` 声明 `permission_scopes(session, user)`，由认证 Repository 仅对租户已启用的插件收集，接纳仍有效的权限目录项并复用范围合并。提供器查询由拥有模块的 Repository 实现；knowledge 根据直接账号岗位绑定仅补充知识读取、编辑的组织范围，资源许可仍逐请求校验。用户岗位选择是 L1 用户表单字段，不再挂载 HR 员工局部表单。

位置信息作为 inv 内部共享模块提供一个维护菜单，资产、仓库和 EDU 巡查共用；沿用现有 inv 交付及迁移流程。坐标必填及历史位置关联见位置维护说明（开发仓库/插件中的 `location-master-design.md`，未随纯底座分发）。

`MenuDef.display_parent_from_catalog` 可显式开启授权导航的旧默认父级展示兼容：只匹配 `previous_parent_keys`、原路径与组件，目标目录及祖先必须有效；计算授权祖先时采用新父链，不增加未授权叶节点，不修改 ORM 原对象或数据库菜单，自定义挂载保持原样。未开启的菜单仍按原父级展示，目录同步规则不变。

开发服务会监听已部署插件的 `frontend.json`，变更后重新读取前端清单、失效相关虚拟模块并刷新页面；部署组合变更仍需重启，不自动安装或开通插件。
