# AI 插件接入任务单

本文件约定 AI 可协助解决源码适配问题；接入不依赖 AI。使用者提供业务源码、插件 key 和目标，不承担逐文件手工改造工作。机械步骤优先用 `convert`，其余通用工具已有 `scaffold / check / revision / pack / inspect-package / install`。先看 [脚本转换说明](plugin-script-conversion.md)，不要人工重复脚本已经能做的步骤。

安装、按依赖生成迁移、正式出包、部署、租户启用和验收的具体命令统一维护在 [通用插件集成手册](business-plugin-integration.md)；本任务单只补充 AI 适配和交付要求，不为某个行业维护另一套开通流程。

## 输入与交付

### 插件化任务范围

- 先核对现有页面、API、Service、Repository、模型和历史调用链，再判断缺口。已有实现只修复插件声明、依赖、路由、字段适配及打包遗漏，不把它改成“待开发”。
- 页面未绑定当前通用接口，不代表整个业务没有实现；先查是否已有独立接口。只有模型或 mock 的情况也应分别说明，不能称为完整业务已经可用。
- 缺少的业务前后端、业务流程和数据模型只列入接入报告；插件化任务默认不补写这些功能。需要业务开发时由用户另行指定。
- 保留现有界面；没有可绑定的真实接口时明确提示“接口未绑定”，不发起无效请求，不用 mock 冒充真实数据。

最少输入：插件 key、名称、L2/L3、源码位置。缺少依赖声明时从实际 imports、模型外键和公开 Service 查证。不能仅依据旧文档认定某能力已经实现。

交付物：

1. 适配后的源码与 `plugins/<key>/plugin.toml`、`frontend.json`。
2. `dist/plugins/<key>-<版本>.zip`；附插件范围、依赖、第三方依赖及接入缺口说明，区分已有实现未接好与确实缺少业务实现。
3. 已生成/未生成迁移、已执行/未执行升级、已启用/未启用租户的真实状态。
4. 从纯底座导入该包的实际验证结果，以及可直接执行的使用步骤。
5. 领域/数据库主设计统一维护在 plugins/core/docs/foundation-platform/，标明历史和规划内容，与当前模型、迁移路径及实现差距建立映射；插件 README 提供主设计入口，插件 docs 可携带说明或副本并保持同步。不可只移植代码而遗失业务设计；纯底座导出仍排除行业设计。

## AI 按此顺序执行

### A. 检查现场

- 读 `AGENTS.md`、当前底座边界、数据库规范和插件加载实现；检查 Git 工作区，保留已有改动。
- 阅读源码、路由、ORM、目录、初始化和前端引用，列出本插件拥有的模块、表、页面及外部依赖。
- 旧业务的历史迁移留在原备份；新 core 分支只用于新库，不能伪装成旧数据库升级方案。

### B. 完成源码适配

- 新交付统一采用 `source_layout = "contained"`，业务后端、管理端、小程序与资源均在 `plugins/<key>/`；稳定 Python 导入名和菜单逻辑路径不变。详见[源码目录](plugin-source-layout.md)。已是 contained 的工作目录直接修正后 check/pack，不再 convert。

- 已有旧 plugin.toml/frontend.json 的业务先用 `convert --plugin <key> --source <源码根>`，输出会转换为独立目录；在 workspace 中处理报告后运行 check/pack。无需重复人工搬目录或登记。

- 新插件可用 scaffold；已恢复旧源码时不要用 scaffold 覆盖它，直接完成适配。
- 清单声明模块、路由、表前缀、权限菜单归属、AI 提供器、独立迁移路径。物料等共享前缀的表按模块拥有者划分，不能按前缀猜归属。
- 拆掉旧学校、固定租户 schema、角色名和旧菜单父级的依赖。跨插件协作使用公开 Service，并在 requires 声明依赖。
- 字典和正常必需配置幂等注册；演示数据单独维护。不要用启动时 create_all、手工补表或 stamp 代替迁移。
- 管理端组件、API 字段、跳转地址和隐藏表单路由保持一致；所有被引用的帮助组件必须随包可用。
- `frontend.json` 声明页面根和小程序提供器。插件私有辅助代码放进已拥有目录；外置 API 等在 TOML `package_files` 明确登记。当前额外文件支持以插件 key 开头的 `web/src/api`、`miniprogram/src/api` TypeScript 文件及本插件 Python 集成模块；AI 快照是环境产物，不提交、不打包，目标环境迁移后显式同步。
- 不修改底座外壳来硬编码插件入口；如确实缺通用扩展点，做通用修复，并验证空组合仍可构建。
- 根据源码证据分别记录接口未绑定、已有实现和缺少实现；不在插件化任务中补写缺失业务，不复制本地 mock 数据来冒充真实库存或真实查询。

### C. 迁移与 AI 元数据

- 生成迁移前检查当前授权；未授权时问清“只生成文件”还是“执行数据库升级”，其余独立工作继续。
- 全新且尚无迁移分支的真实模型插件，可在授权后离线生成：

```powershell
# plugins/core/backend/；schema 参数仅校验命名，本模式不连接数据库
& '.\.venv\Scripts\python.exe' -m app.framework.plugin_cli revision --plugin <key> --schema t_default --message "initial plugin" --from-models
```

- 审核建表、外键、约束、中文注释及降级顺序。离线生成器只取本插件 ORM 表，不推断触发器、视图、存量数据变换或自定义 SQL；这些必须另行设计和审查。无业务表的示例插件可生成空分支。
- 已有分支不能再用 `--from-models`；用 `--autogenerate` 对照已升级的开发库生成增量，读取目标库也须先确认。
- 发布 AI 表查询资源前逐项登记权限、范围和字段保护，不因新增表而自动放行。静态接口快照可通过 `harness_http_cli sync --plugin <key>` 离线生成；表快照同步和检索重建遵守独立 CLI 及目标授权规则。

### D. 校验、打包、导入验收

- 用 `check --require-migrations` 校验；执行与改动相关的后端测试、管理端类型检查/构建、小程序部署裁剪检查/构建。
- 用 `pack` 输出包，`inspect-package` 检查；导出一份无业务源码的纯底座，在隔离目录中 `install --deploy`，确认页面、部署和源码自动接齐，再运行 check。导入源码本身不执行包内代码；导入后 check/服务启动会执行可信插件代码。
- 仅在获得执行授权且确认目标库/租户后进行真实安装验收；否则明确停留在“源码包就绪，待目标库开通”。
- 最终告诉用户包在哪里、下一条命令是什么、哪些未完成；不要把“还有十几个文件请你手动修改”作为完成结果。

## 工具边界

源码包是构建期集成，导入后重启/重新构建。`install --deploy` 自动合并源码、页面登记、部署依赖和 `.plugin-lock.json`，不执行迁移、装依赖、热加载或发布上线。

源码适配与包导入分两次完成：一次将旧业务变成可移植包，以后各底座实例只导入包。无需为每个业务复制一套安装器。
