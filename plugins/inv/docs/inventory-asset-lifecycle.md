# 物料、库存与实物资产闭环

2026-11-12：新收货确认时同步登记资产；按业务规则移除“历史入库补登记与核对”和“旧资产地点补关联”的入口、前端组件、接口及补办逻辑。业务仍属于 inv 内的 inventory、inventory_requisition、asset_management，没有新增应用或财务核算。

## 报废接管与责任闭环

转报废同时完成后勤接管：从当前租户有效登录账号中选择后勤接收人，提交账号 UUID；服务端重新校验其有效成员身份、实际维修处理或报废处置权限及资产所属组织的访问范围，并从账号当前有效部门带出责任部门。接口和页面不按管理员、后勤等角色名称旁路授权，也不接受客户端填写接收人姓名或责任部门。实际处置经办人另选具有报废完成权限的有效账号；当前操作账号在可选范围内时默认带出，姓名由服务端保存快照，实际点击操作人仍保存在审计字段。

已确认的关联单件资产接收后进入 `asset_status.pending_disposal`（待报废处置），责任部门和保管人转为所选账号的有效部门及本人，固定位置和个人使用地点说明清空，资产组织权属保持不变。原位置、责任部门、保管人、状态和个人地点说明保存在资产变更事件中，报废单引用具体事件及接收后的资产版本。资产写入只能经资产模块公开 Service，在同一事务保存维修终态、报废单、责任移交、附件和进度；任何校验、证据绑定或状态回传失败全部回滚。

待报废及已报废资产从报修和库存实物候选中排除，提交和库存过账再次校验；普通调拨、移交、作废登记及其他业务状态变更不得绕过对应报废流程。在库实物仍须按库存报损办理，接收动作不能清空仓库实物分配或悄悄扣减库存。直接登记关联资产同样办理接收；正在维修的资产须从原维修单转入。无资产台账的设备只保存接收账号及部门，不伪造资产记录。

完成处置须选择实际经办账号，填写方式、日期、说明并上传至少 1 张、最多 6 张处置凭证。单据标记已处置，关联资产标记已报废；保留最后保管人、部门、申领、维修、库存来源、附件和事件历史，以终态结束有效保管责任。既有有效资产及离职待交接查询排除已报废设备，不能再次领用、报修、交接或退库。

仅待处置单可作废：核对接收事件归属、资产版本和当前责任，恢复本单接收前的位置、保管人、部门、个人地点说明及状态，并追加回退事件；维修来源恢复原维修状态。责任已变化、原对象失效或已完成处置时拒绝自动覆盖。作废记录及附件保留，来源维修单可再次转报废；部分唯一索引只约束未作废的来源记录。新增的维修进度外键将每次转报废照片绑定到各自进度，避免重办后覆盖旧照片投影。未建立进度关联的历史记录保留原有投影兼容，原报废详情仍可追溯。

历史待处置记录不自动转移责任。完成时若缺少接收账号或移交事件，页面要求显式补选接收人，在同一完成事务补办接收再完成处置；历史数据矛盾或在库约束不满足时须人工核实。旧已处置记录仅保留原姓名快照，不补造经办账号或移交历史。

### 数据库升级

EDU 集成场景在 的 `asset_disposal` 增加 8 个可空字段：`receiver_user_id`、`receiver_name_snapshot`、`receiver_department_id`、`receiver_department_name_snapshot`、`custody_event_id`、`custody_asset_version_no`、`handler_user_id`、`source_repair_progress_id`；inv 的 `asset_change_event` 增加 `from_custody_location_note_snapshot varchar(200)`。账号、部门、事件和维修进度均有显式外键；原来源维修工单唯一索引调整为未作废记录的部分唯一索引。原表名及已发布迁移保留，保留历史对象名称。

已同步 `data-dictionary/tools/dd_spec.py` 对应结构和业务规则；原字典无法完整表示当前工单域外键及部分唯一索引，实际 ORM 是最终迁移定义，字典中已注明差异，未运行全量模型或设计产物生成器覆盖源码。目标环境先备份，执行以下步骤，`t_actual` 替换为实际租户：

```powershell
python scripts/erp.py db revision --plugin edu --schema t_actual
# 审核 inv/edu 增量：上述 9 个字段、外键删除行为，以及来源索引的部分唯一条件。
python scripts/erp.py db upgrade --plugin edu --schema t_actual
python scripts/erp.py dev sync --plugin edu --schema t_actual
```

`edu` 包含 inv 依赖，按依赖顺序处理；开发配置同步补齐 `asset_status.pending_disposal` 字典值，生产环境沿用数据库维护及插件开通流程同步必需字典。升级和同步完成后重启后端、更新管理端。启用 Harness 的环境再显式运行 `python scripts/erp.py ai sync --schema t_actual`；需要调用向量模型时另行授权添加 `--index`。新快照仅用于回退，不扩充 AI 人工字段白名单。

新记录的原维修状态从显式关联的转报废进度读取，不再写入 `flex_form`；作废旧记录时仅兼容读取原有状态值，不批量改写历史扩展信息。

## 设备报修表单

小程序“提交设备报修”默认先搜索、选择资产设备。设备目录以报修人当前主组织为默认范围，并包含权限范围内本人当前保管的跨组织个人设备；只提供已确认登记、未删除、未报废的单件设备，名称、编号、位置支持搜索和分页。接口不要求资产台账管理权限，也不额外授予资产管理能力。历史按数量资产、水电及门窗等无单件档案设施，通过“未找到设备 / 其他设施”填写设施名称、类别和完整故障位置。

补充修正：任课教师演示角色的默认范围是 `related`，原实现未登记资产保管关系，通用过滤因此拒绝全部候选；此前固定主组织的条件也会漏掉共享仓库发放的个人设备。现由资产模块注册单件资产的关联范围：当前保管人须为本人，固定地点设备须处于其可访问组织，个人保管设备按同租户内的当前保管关系读取。建档人或历史申领人不等于当前保管人，移交后原保管人不能继续选择或新建报修。选择、按编号匹配及按 ID 提交均复用同一关系过滤，不按角色名称旁路授权。

普通设备报修的工单组织由服务端读取的资产权属确定，共享仓库设备不转移到申领人的主组织；后勤继续按工单组织授权处理，原上报人按既有本人契约查看、撤销和验收。跨组织时不使用上报人主组织名称冒充设备校区。其他业务来源显式指定组织的建单契约仍要求资产与来源组织一致。

选择后以摘要展示名称、编号、登记位置及可确定的类别。资产字典 `teaching_equipment` / `it_equipment` / `furniture` 分别映射报修类别 `teaching` / `it` / `furniture`；通用设备、器材及其他未匹配值仍须选择类别，不按设备名称猜测。位置补充仅存入本次工单的位置文本，不修改资产档案；个人保管设备没有位置说明时须补充实际故障位置。提交只需资产 ID、故障、照片、紧急程度和本次联系方式，服务端在当前事务重新校验资产、确认状态和范围，补齐可信字段，不能依靠客户端摘要改写资产身份或地点。

`/api/repair_order/form-context` 只提供当前登录人的姓名和联系电话，优先读取有效人员姓名和人员联系方式，无人员电话时回退到其认证账号手机号。用户模块通过同时绑定当前租户用户 ID 和认证账号 ID 的公开只读契约提供，不接收待查人员 ID。缺失信息提示补填，允许临时修改本次联系人；不写回账号或人员档案。故障照片仍至少 1 张、最多 6 张，单张最多 10MB。

资产候选通过 `/api/repair_order/asset-options` 及资产模块公开引用目录获取，仅返回资产 ID、名称、编号、类别和位置；不返回保管人、电话、原值或其他资产详情。新接口继续使用原报修权限、租户上下文和字段保护，不扩充 AI 人工白名单。

本项没有表或字段变更，无需生成或执行迁移；更新、重启后端并重新构建发布小程序/H5。使用 Harness 的环境由用户按实际租户运行 `python scripts/erp.py ai sync --schema t_actual` 同步接口快照；需调用向量模型重建索引时另行显式添加 `--index`。

## 管理口径

物料定义名称、规格、单位和管理规则；库存记录仓库、批次、库存状态下的数量；资产记录实物身份、使用位置及责任。实物资产管理不代表财务固定资产认定。

复用物料 `is_asset_managed`：关闭时按普通物料入库；开启时新收货确认同步登记并确认资产。资产物料只需配置 `default_asset_type_code`，所有新资产（包括桌椅等家具）统一逐件编号。`default_asset_management_mode_code` 仅作历史兼容，新写入固定为 `individual`，旧值不再控制新收货。来源保存资产类型、固定逐件登记方式及库存状态快照。

关闭资产开关不会删除已登记资产或实物关联，也不能绕过出库时的实物选择校验。已有资产流转不要求重新打开物料开关。资产台账使用独立的简洁登记入口：选择仓库时同步库存，不选仓库时只建立资产；已有独立登记记录仍可查看、编辑及按原流程办理确认或作废。

库存和资产数量有重叠：购入 10 台电脑、领用 6 台后，仓库库存为 4 台，资产总量仍是 10 台，两者不能相加。

库存余额的 `org_id` 必须与所属仓库一致，不能沿用入库单的上级组织。统一记账入口在资产追踪、余额数量及流水变更前检查本次涉及物料和仓库的余额组织，入库、出库、调拨、借还、盘点及冲销均适用；复用余额时再次核对组织。发现历史归属不一致返回 409，并提示管理员核对修正，不静默转移库存，也不通过放宽查询范围掩盖差异。核实并授权后可定向修正异常余额的组织，同时保留数量、预留量、批次、状态及历史流水，留存修正前备份并更新审计字段和版本号。此项校验没有模型或接口结构变化，无需生成迁移或重建 Harness 目录与索引。

## 简洁资产登记与入库自动登记

资产台账点击“新增资产”以居中弹窗打开独立 `AssetRegistrationForm`，不再复用完整入库单表单。弹窗按“资产信息”和“责任与存放”分组，宽屏并排排列主要字段，窄屏自动换行；内容超出高度时滚动填写区，底部数量、原值汇总及保存操作保持可见。字段为所属组织（默认当前组织，多组织时可选）、资产编号（空值自动）、资产物品、整数数量、目标仓库（可空）、责任部门、资产保管人、资产位置、单件原值、备注；“更多信息”仅包含购置日期与资产状态，不提供出厂序列号。一次最多登记 1000 件同种物料，多件分别生成唯一编号，单件允许手填编号并校验重复。选择资产物品时，将物料参考单价带入单件原值，允许手动修改或清空；切换物料按新物料重新带价，切换组织清空原值。物料参考单价未设置时保持空值；单件原值为空表示未知，零表示已知为零，批量同值并展示合计。物品候选接口返回可空的 `unit_price`，金额以十进制字符串传输。

`GET /api/asset/registration-options` 和 `POST /api/asset/registrations` 均要求真实资产新增与确认权限；未选仓库不要求库存权限，不产生库存单据或余额。部门、保管人、实际位置必填，状态可为闲置或在用，服务端在同一事务逐件登记并确认，任一件失败全部回滚。物品候选使用已有资产资格筛选，`/api/asset/item-options` 支持显式 `permission_key=asset_register:create`，仅持有查询权限不能冒用新增范围。

选择仓库时还须具备入库新增和确认权限，并取两种权限的组织及记录范围交集。默认带出仓库责任部门、资产保管人和统一位置；部门与保管人可调整，位置固定为仓库位置，状态固定闲置。服务端调用 inventory 公开组合事务能力自动创建并确认“其他入库”，原因为“资产登记入库”，不提交中间事务，不另写库存表。编号、购置日期与单件原值保存在资产拥有的入库登记配置表，由原过账扩展同步建卡，备注随明细带入。原值未知时库存单价也保持未知，不套用物料参考价或伪装为零。独立于仓库登记的资产不计入仓库库存，沿既有独立资产交接流程管理；不会伪造库存来源。

仓库档案新增可选 `default_asset_custodian_user_id`，选项仅发布已授权根组织本级及有效下级组织的启用用户 ID、显示名、归属；不读取证件、联系方式或人员私密字段，不扩充下级组织业务记录或 AI 字段访问权。选择器按当前仓库新增/修改权限和组织加载，忽略迟到响应，失败可重试。部门与保管人引用在保存与实际登记时重新验证；缺少默认值可在本次登记中手动补选，不能自动使用当前登录管理员。

入库管理继续使用完整收货表单，新收货始终逐件编号，批次号只用于收货追溯。新增资产和入库表单均不提供 CSV 明细导入；旧 `/api/inventory_stock_order/import_lines` 返回 404。物料档案的 Excel 功能保留，模板为 14 列，取消建议登记方式；旧 9 / 12 列保留未提供的资格和类型，旧 15 列仅接受空白或单件方式，不能恢复数量管理。历史数量资产仅兼容查询、减少、交接和退库，不自动拆分或清除。

新增四个可空字段与相应约束，需用户先完成目标环境增量升级：

```powershell
python scripts/erp.py db revision --plugin inv --schema t_actual
# 审核 inv_warehouse.default_asset_custodian_user_id 及外键，
# asset_stock_registration_plan.asset_no / acquired_date / original_amount 与原值非负约束。
python scripts/erp.py db upgrade --plugin inv --schema t_actual
```

将 `t_actual` 替换为实际租户，升级后重启后端并刷新管理端；在仓库档案维护默认资产保管人，或在新增资产时手选。未生成或执行真实库迁移，未自动关联人员、转换或清除业务数据。`dd_spec.py` 已同步字段；启用 Harness 的环境在迁移后由用户显式执行 `python scripts/erp.py ai sync --schema t_actual`，需重建索引时在模型配置完成后加 `--index`。

简洁登记验证：后端 252 项、前端 37 项及管理端类型检查通过，应用导入通过。覆盖选仓库与不选仓库、单件手填及多件自动编号、未知/零/已知单件原值、购置日期和备注、默认与手动责任、下级组织保管人、组织/本人范围、失效用户、编号冲突完整回滚，以及旧资产流转回归。已通过隔离浏览器验证两种保存路径与窄屏布局，未在真实业务库登记资产。

目标仓库在入库单选择一次，资产位置直接继承仓库的统一物理位置。资产物料过账前检查位置是否同组织、启用且未删除；配置不完整时提示维护仓库档案。普通物料继续兼容尚未配置位置的仓库。

仓库页面统一显示“责任部门”，内部字段仍为 `default_asset_department_id`，入库时作为资产责任部门默认值带出，不按名称硬编码或自动匹配。可选仓库所属组织本级及其所有有效下级组织中的启用、未删除部门；部门树的下级部门同样可选。上级组织的仓库可选本组织和下级组织的部门，分支仓库的候选范围从所属组织向下计算。入库明细允许本次调整，配置保存在资产拥有的 `asset_stock_registration_plan`，不放入 `flex_form`。保管人可选，沿用原有身份和数据范围校验；资产责任不从旧位置默认值推导。

部门选项通过 `/api/inventory_warehouse/department-options` 按 `org_id` 和当前动作的 `permission_key` 查询。服务端仅接受已授权的仓库新增/修改或入库新增/修改/确认权限，先校验根组织操作范围，再通过组织模块公开的 `descendant_ids_query` 获取有效组织子树。返回部门 ID、名称和归属，并以“分公司 / 行政部 / 设备组”等路径区分同名部门。停用或删除的组织分支及无效部门不参与候选。

部门是目录引用，不能将仓库或入库单的本人范围误套到部门创建人，也不能优先选中另一个操作的权限。对根组织的管理授权只允许查询、引用下级部门目录，不自动授予下级组织的库存、资产或人员业务数据权限。仓库保存、详情回显、入库默认责任部门、本次责任部门覆盖及逐件资产自动登记均复用 `warehouse_department_reference` 契约。资产及库存的 `org_id` 仍属于来源仓库组织，不随责任部门改变。

仓库编辑与入库表单共用选择器，切换组织或权限时重载并忽略迟到响应；请求失败显示原因和重试，成功空列表显示“本组织及下级组织暂无可选部门”。此前的部门层级范围修复本身不依赖迁移；仓库保管人及登记元数据字段需要按上文升级。未修改真实部门或仓库数据。

确认入库在同一事务完成：库存记账、生成 `asset_stock_receipt` 来源记录、创建或合并资产、确认登记、建立 `asset_stock_binding` 实物分配。任一步失败全部回滚，草稿不建卡。

- 单件数量须为整数，两台电脑生成两张已确认卡片；编号为 `ZC-日期-完整UUIDv7`，由组织内唯一索引兜底。
- 新收货数量必须为整数，物料原方式为 `batch` 或空也统一逐件编号；普通非资产物料仍可按公斤等单位登记小数数量。逐件建卡中任意一件失败，整次库存、来源和资产创建全部回滚。
- 新收货来源累计登记量等于收货量，入库详情显示登记进度；不产生需要用户另行补办的登记步骤。
- 正向盘盈同样自动登记；新收货不能直接记为借出状态，先入库再办理借出。盘亏须核对实物并办理报损。
- 自动登记校验真实 `asset_register:create`、`asset_register:confirm` 权限及范围，不由库存确认权限旁路。

建卡现在只由库存过账事务调用内部 `_register_received_asset`。不提供独立的收货补登记、期初关联、解除关联或来源补办清单接口。

采购入库（`PURCHASE_IN`）只用于新收货，资产列显示自动登记和责任部门，不显示“关联资产”。服务端在任何库存余额或流水变更前拒绝该类型携带已有实物选择，不能通过直接请求把采购记成原资产退库。旧采购草稿若已有选择，管理端明确提示清除错误关联或改用其他入库，保存前拦截，不静默丢弃原选择后新建卡片。

其他入库（`OTHER_IN`）可用于新收货或已有资产退库：新收货保留自动登记；原资产退库使用“选择退库资产”，选择已领用原实物并按原编号入库。借用归还使用“选择归还资产”，对应原借出明细；领用、调拨等页面保留“关联资产”。弹窗标题和提示随用途变化，不新增单据类型或数据库字段。已存在的实物选择本身也会启用资产流转校验，物料后来关闭资产开关时，退库仍同步原资产，不能只改库存。

## 出库、调拨、借还与退库

库存明细通过通用 `tracking` 扩展协议提交 `asset.selections`，关系保存在 `asset_stock_selection`。库存模块不反向导入资产模块；所有库存公开过账调用（含 EDU 申领发放）均经过追踪扩展。

同一事务内重新验证实物的组织、权限范围、物料、批次、仓库、库存状态和已确认状态；选择数量须等于本次库存变化数量，单件不能拆分。批次扣减依据选择的实物，避免默认先进先出扣错来源。

独立库存领用、借出指定交付位置、责任部门和可选保管人；通过物资申领发放给个人时按下述个人保管规则执行，不要求固定地点。仓间调拨和退库沿用目标仓库位置。出库减少仓库库存但保留资产身份；退库选择原实物，不新建卡片或累计收货登记量。借出将 available 转为 lent，归还转回 available；归还须沿实物来源链对应原借出明细，不再提供期初借出缺失身份的兼容匹配。

历史数量资产保留部分领用、退库和来源拆分兼容；同位置不能用一个台账表示多组不同责任。跨组织权属转移不属于本次范围，仓库共享申领授权不等于资产权属转移。库存流转、资产变化和来源分配一并成功或回滚；签收独立办理且不再次扣库。

已关联在库实物不能通过独立资产移交或调数量绕过库存。已领用资产的正常责任交接和资产调拨继续可用，并同步来源分配。

## 作废、冲销与已移除功能

入库自动生成的资产不能单独作废登记或释放来源额度；更正须通过相应库存或资产流转办理，避免在库有数量却失去资产关联。管理端对这些资产不展示“作废登记”，服务端也拒绝直接调用。独立新增资产的原登记作废流程保留。

已经关联资产或发生实物流转的库存单不能独立冲销。没有已登记来源的普通库存单继续按库存原规则处理。

已退役的入口：

- `StockReceiptDrawer.vue`、`AssetLocationBinding.vue` 及对应 API 客户端、入口和未使用状态。
- `/api/asset/stock-receipts` 及补登记/来源明细子路由、`stock-opening-options`、`stock-openings`、`unlink-opening`。
- `/api/asset/locations` 的旧地点维护 HTTP 路由、旧地点待关联筛选和手工改绑处理。
- 期初余额候选查询、任务创建、历史卡片挂接、解除关联和来源恢复；归还对期初缺失来源的匹配分支；作废后释放收货额度再补登记的流程。

正常资产登记仍直接选择统一位置，内部资产位置配置按需自动建立；已有配置不能补关联或改绑。位置主数据更新时的投影同步、引用保护及正常资产位置筛选保留。

旧功能移除未清理测试数据、删除历史字段或改写旧迁移。`source_balance_id`、原期初来源快照和旧位置引用等列仅保留已有存储，不再有补办写入路径。旧测试记录不会自动修复或重新建卡，由用户后续另行清理。资产登记所需增量字段和约束见上文升级步骤。

## 个人申领与流动保管

个人账号的资产申领在后勤确认实际发放时转为个人保管；保管人由服务端从原申请确定，不按教师等角色名称分支，也不允许发放参数覆盖为其他人。责任部门优先取申领人当前有效部门，未关联部门时保留该件资产原部门。小程序填写的使用地点为可空的 `custody_location_note`（最多 200 字），只作补充说明，不建立物理位置或持续定位。

`asset_register.location_id`、`asset_location_item.location_id` 为空表示个人保管，此时 `custodian_user_id` 必须非空；固定地点资产继续引用原位置。两张资产表增加稳定的 `custody_reference` CHECK，禁止既无固定位置又无保管人的记录。资产台账及详情显示“个人保管 · 保管人”，同时展示选填地点；查询使用外联接，避免个人资产因没有固定地点而消失。历史数量资产按实际发放量拆出个人保管分配，不按空位置合并不同人的责任。没有新建个人虚拟地点，也没有改写历史单据或批量清空旧资产位置。

共享仓库可向仍在有效共享范围内的其他组织发放。发放事务只核对原申请人、其有效组织和部门、仓库共享关系及原出库单绑定，不扩大人员目录访问范围，也不授予申领人资产调拨权限。资产、库存及实物来源的 `org_id` 保持原仓库组织。停用账号/组织/部门、已撤销/尚未生效的共享、无关组织、伪造出库来源及缺少资产流转权限均拒绝发放。

发放仍须选择已确认的具体实物；后台在同一事务扣库、设置个人保管、保存来源分配与事件。照片绑定等任一步失败全部回滚。普通耗材继续只记数量。签收和异常反馈不再次扣库或转移资产。原资产退库时恢复目标仓库位置、采用本次退库责任并清除个人地点说明，不生成新资产卡片；交接明细的 `from_location_id` 允许为空，同时保留原责任人。个人使用地点及新保管明细不进入申领的 AI 投影，未扩大字段白名单。

### 资产候选与提交的组织一致性

已发现的历史情形是：申请单、当前仓库及库存余额属于校区，但旧资产台账、资产收货来源和实物分配仍属于上级学校。原下拉候选只限定仓库与操作人可见范围，没有核对这些归属是否一致，因而全范围账号能选中随后被发放校验拒绝的资产。跨校区申领授权只允许个人保管，不代表可以改变资产权属或绕过当前仓库的归属校验。

候选查询现于计数和分页前同时核对实物分配、收货来源、资产台账及当前仓库的组织，校验台账与来源物料一致；已出库资产的候选不强制存在当前仓库，正常同组织仓间调拨仍沿用原来源。保存、准备过账及过账共用物料/组织核验，物料不一致与归属不一致分别提示，不能通过提交缓存中的旧候选绕过。未放宽组织范围或自动修改历史数据。
